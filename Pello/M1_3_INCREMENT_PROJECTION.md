# M1.3 — Later-stage increment context projection

## Baseline and boundary

The starting branch was `codex/pello-phase3c`, HEAD and locally recorded upstream both `6c293de279fd1a4cef2c3937ecf32b463300b9f6`. Pre-existing untracked files were preserved. Remote synchronization was verified separately by the coordinating session. M0, M1.1 and M1.2 reports and implementations were inspected.

`planner_input` checks the accepted analysis against persisted source and sends the complete `AcceptedAnalysis`: product objective, requirements, source segments, issues, assumptions, exclusions/instructions and their identifiers, dependencies, provenance and approval metadata. `propose_increments` adds the architecture's work nodes and global requirement IDs, objective, tool catalog and optional review feedback. Each node carries its own objective, requirements, dependencies, optional dependencies, resource prerequisites and operation kind; those fields are not copies of entire requirement objects and are essential to its distinct task association. Requirement descriptions and source text can overlap in meaning but are distinct representations; none was deduplicated or equated. Requirement dependencies and node dependencies have distinct scopes and directions. `_invoke` journals the unmodified input envelope, constructs `_prompt`, and passes that actual prompt string to `backend.run`; validators and canonical persistence still consume the unprojected data. The evidence envelope is not itself the model-bound prompt.

Architecture also supplies the complete analysis, while contract planning supplies it with expanded increments and can batch. Original preserved largest prompts reported by M0 were architecture E 54,043, increment I 53,834, and contracts I batch 1 51,736 characters. None proves that these stages contain identical semantic objects suitable for merging. Increment planning has a directly measurable, repeated transport cost: each requirement repeats the same field labels, even though each value and ID is distinct. Factoring the labels once into ordered columns preserves every value, whereas deduplicating descriptions or sources would assume meaning or reference equivalence. Only this boundary is changed.

## Change and measurements

`athis_autopilot/product_planning.py` adds a narrowly scoped projection for `plan-increments` and revisions r2/r3. It encodes the requirements list as ordered column names and one distinct row per original requirement, with explicit reconstruction instructions. It verifies canonical typed analysis and references, unchanged source hash, valid work-node structure and IDs, dependency references, reserved markers and exact serialization round trip. It uses the representation only when the original prompt fits within 55,000 characters and the projected prompt is smaller. Larger inputs retain the prior generic packing and rejection behavior; invalid, noncanonical, unsupported, conflicting or non-beneficial inputs fall back. This conservative threshold deliberately does not claim to resolve historical context-limit failures. No work-node field is transformed.

## Verification and limitations

New `tests/test_m13_increment_projection.py` covers reversible reconstruction and deterministic serialization, no mutation, shared associations, individual contradictory requirements, blocking issue, provenance and approval fields, requirement/task dependencies, r2/r3 feedback, invalid identifiers or references, duplicate tasks, unsupported fields, reserved markers, malformed types and prior oversized-context fallback. Existing validators and protected tests are unchanged. Targeted tests: 35 passed. Complete offline suite: `.\.venv\Scripts\python.exe -m unittest discover -s tests`, 280 passed in 283.534 seconds. Independent Reviewer technical verdict: **PASS** after identifying the dependency wording defect and the two additional preserved fixtures; both were addressed and independently rechecked.

Deterministic reconstruction establishes information preservation, not equivalent model interpretation. The model must correctly interpret the ordered rows; a separate controlled semantic A/B evaluation should compare original and projected prompts against original sources, with independent review of requirement coverage, dependency direction, blocker scope, authorization and provenance. Historical context-limit failures remain unresolved. M1.2's three inference pairs do not establish statistical equivalence, and prompt-character savings did not imply comparable SDK input-token savings. M1 is not complete.

Separate provenance reminder: M1.2 observed customer-approval labels without explicit source approval evidence. This is an unresolved concern in both variants; this change neither promotes nor repairs those labels.
